# ADR-009 — Dispatch entries that can never fire: retire, re-key, then hook

- **Status:** accepted (2026-10-10)
- **Context source:** KNOWN_FINDINGS F16; umbrella `registry/DEAD_ENTRIES.md`
  (`registry/check_dead_entries.py`), `registry/ENTRY_STATE.md`.

## Context

`cpu.c` hooks exactly two opcodes, `JSR abs` (0x20) and `JSL long` (0x22): a
dispatch entry runs only when one of them targets **exactly** its PC. The
2026-10-10 audit cross-checked every entry against all direct JSR/JSL targets
in the ROM, dispatch hits on the 14 fixtures, and by-name calls from ported C
parents. 129 of 204 entries can never fire (112 of them credited L2):

| Class | Entries |
|---|---|
| Jump-table targets (`jsr (abs,x)` / `jmp (abs,x)`, not hooked) | 47 |
| Wrong bank, PC holds `$FF` padding | 9 |
| Off-by-2 (a direct caller targets PC±2) | 5 |
| Same address called from another bank, or caller at PC±3..16 | ~19 |
| No direct caller at all (JMP/JML/fallthrough, data-modeled banks $12-$16) | ~49 |

The registry's levels therefore measure *proven C bodies*, not native
coverage, and several documented fixes never executed in game (TfrInvertPal's
manual DMA loop, TfrVRAM_c's delegation fix). Every JSR/JSL miss also scans
the whole table linearly, so dead entries cost interpreter time on the device.

## Decision

A progressive, mixed remediation:

1. **Retire now** the entries whose PC holds padding — certainly unreachable,
   zero behaviour change. Done 2026-10-10 for 9 entries (`D00FFE0` and the
   eight bank-$12 entries incl. `D12EE35 TfrInvertPal_c`), registry →
   `RETIRED`, tombstone comments in `dispatch_all.c`, `FF4_DISPATCH_COUNT`
   204 → 195. FB/WRAM signatures identical on all 14 fixtures; vanilla and
   J2e `regress.sh` verdicts unchanged.
2. **Re-key progressively** the entries whose true PC is proven by the ROM
   (off-by-N, wrong bank). A re-keyed entry runs natively for the **first
   time**, so each one goes through the full chain before landing: strict
   spike at the true PC (`generate_spike.py --target-addr`), oracle on a
   fixture that exercises it, device liveness check. One routine per commit.
3. **Hook `jsr (abs,x)` / `jmp (abs,x)` only after measuring the gain**,
   behind a per-routine gate. The interpreter is ~5 % of device frame time
   (PLAN-SUBFRAME.md); the speed lever is the PPU render path. Activating 47
   never-exercised bodies at once is the riskiest option for the least
   measured benefit.

`check_dead_entries.py` is re-run after every dispatch-table change
(ff4-status §1b); a `DEAD` routine is not promoted further until re-keyed.

## Alternatives rejected

- **Retire all 129 at once** — honest registry, but throws away the re-key
  shortcut for ~24 entries whose true PC is already known, and the ~49
  "no direct caller" entries need a per-routine read of the asm first (an
  indirect-call target is reported dead by construction).
- **Hook the jump tables first** — see decision 3.
- **Keep the table, only flag entries** — keeps paying the linear scan and
  keeps the registry misleading.

## Consequences

- Registry L2 counts drop as entries are retired; that is the point.
- Re-keying is real porting progress (native code runs for the first time)
  and carries real risk: it follows WF-DECOMP + WF-VALID + WF-RELEASE, not a
  table edit.
- Variant profiles (`rom_profiles.c`) are regenerated by `patch_impact.py`
  on every table change (gate array is per slot).
